# WP25 agent-launch

## Summary
The desktop console's bar has **▶ Claude Code** and **▶ Codex**. With a
project open in the main window, a click checks the server (MCP on, accounts
on), finds the tool through the login shell's PATH, asks once per project
("Let Claude Code edit “Thesis”?", with "Don't ask again for this project"),
mints a project-scoped access token through the window's session, and opens
the agent in a new console tab. The agent runs in an empty per-project folder
under the profile and edits the project only through the server's MCP tools,
so its edits reach co-authors live with the server's agent marks, Review and
Revert. A missing tool shows an install card (Copy, Type it into the console,
Check again); with no project, MCP off, no accounts or an old server, the
buttons say why. Console Settings has the off switch ("Show the Claude Code
and Codex buttons", default on). On the web, the Connect card gains a Codex
tab, a desktop-console hint, and a bearer-token Claude Code command when
accounts are on but OAuth registration is closed.

## How it works
- **Status** (`console:agent-status`, asked when the page boots, gets focus, or settings change): the project comes from the main window's URL (`ShellCtx.projectFromUrl`); `GET /api/capabilities` through `sessionFetch` gives `mcp` and `accounts` (both already base keys from WP03, so `srv/features/agents` stays a stub). A blocking reason makes the buttons `aria-disabled` with the reason as their title; a click shows it in the card.
- **Detection** (`detectAgent`): `$SHELL -lic` prints the login shell's PATH (5 s timeout); the tool is looked up there and in `~/.local/bin`, `~/.claude/local`, `~/.npm-global/bin`, `/opt/homebrew/bin`, `/usr/local/bin`; the agent runs with that PATH. Windows: `PATH` with PATHEXT; an npm `.cmd` shim runs through `cmd.exe /d /s /c` (untested, no Windows machine).
- **Consent:** `features.console.agentConsent[<server>|<project>] = true` only when "Don't ask again" was ticked.
- **Token** (`tokens.js`): `POST /api/tokens {name: "Laytekz agents · <host> · <project>", projectIds: [id]}` through `sessionFetch` (cookie, no Origin). Stored as `features.console.agentTokens[<server>|<project>] = {id, enc}` with `safeStorage` (memory only when encryption is unavailable). Before each launch `GET /api/tokens` checks the id is still listed and unexpired; a revoked one is replaced. 401 says "Sign in to Laytekz first".
- **Files** (`userData/agents/<host>-<project>-<hash>/`): `mcp.json` (`Authorization: Bearer ${LAYTEKZ_TOKEN}`, `X-Laytekz-Agent: claude`), `prompt.md` (project, branch, use the laytekz MCP tools, compile with `compile`), both 0600, and an empty `work/` the agent starts in.
- **Commands:** `claude --mcp-config <mcp.json> --append-system-prompt-file <prompt.md>` (no `--strict-mcp-config`); `codex -c mcp_servers.laytekz.url="<server>/mcp" -c mcp_servers.laytekz.bearer_token_env_var="LAYTEKZ_TOKEN" -c mcp_servers.laytekz.http_headers={"X-Laytekz-Agent"="codex"} "<prompt>"` (the prompt is Codex's first message). `agentArgs` throws if a bypass flag is ever in the list (`hasBypassFlag`).
- **Environment:** the console's (`shellEnv`) plus `LAYTEKZ_URL`, `LAYTEKZ_PROJECT`, `LAYTEKZ_BRANCH`, `LAYTEKZ_TOKEN` and the login PATH, for the agent tab only. Plain shell tabs never get `LAYTEKZ_TOKEN`.
- **Agent tab:** titled "Claude Code" / "Codex"; on exit, "Claude Code exited. Press Enter to start it again, or close the tab." (restart reuses the spec). An agent tab counts as a running command for the quit question.
- **Test mode** (from source only): `LAYTEKZ_TEST_AGENT_BIN=/abs/dir` makes detection look only there (so a test never starts the real tools); the consent question goes to `<profile>/agent-consent.jsonl` and is answered by `LAYTEKZ_TEST_AGENT_CONSENT` (`allow` default, `always`, `cancel`).

## Deviations
- **Server side:** `srv/features/agents` stays the stub. The plan names its capabilities `mcp` and `oauthRegistration`; WP03 already answers both as base keys of `GET /api/capabilities`, so nothing was left to add.
- **Web feature module:** `web/features/agents` stays the stub; the web part is the Connect card (`ClaudeConnect.tsx`), as plan §3.3 lists. No separate "Agents panel".
- The token is not given an expiry (the Agent access card lists and revokes it; a revoked or expired one is replaced at the next launch).
- Detection reads the login shell's PATH and searches it in JavaScript instead of parsing `command -v` (aliases and functions are ignored; only executables count).
- Codex's instructions are its first message (a positional prompt), the documented way that works across versions.
- No custom agent commands or extra arguments in Console Settings (the report's table lists them): left out so that no setting can add a bypass flag.

## Privacy notes
- **Hosts:** only the configured Laytekz server, through the main window's session: `GET /api/capabilities`, `GET /api/projects/:id`, `GET /api/tokens`, `POST /api/tokens` (when a token is needed). The agents themselves contact the server's `/mcp` and their own vendors (Anthropic, OpenAI) with the user's own accounts; Laytekz sends them nothing else.
- **Stored on this computer:** `settings.json` → `features.console.agentTokens` (token id plus the token encrypted with the OS keychain through `safeStorage`; never in clear), `features.console.agentConsent`, `features.console.agents`. `userData/agents/<key>/mcp.json` and `prompt.md` hold the server URL, project id, branch and project name, never the token.
- **Server side:** each project gets one personal access token named "Laytekz agents · <host> · <project>", scoped to that project, visible and revocable on the user's Agent access card.
- The token reaches only the agent process's environment (`LAYTEKZ_TOKEN`); it is never on a command line, in a file in clear, or in a plain shell tab.

## Operator variables
None in production (the buttons need `ALDINE_MCP=1` and accounts on the server). Test only, from source: `LAYTEKZ_TEST_AGENT_BIN`, `LAYTEKZ_TEST_AGENT_CONSENT`.
