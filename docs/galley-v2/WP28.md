# WP28 rename-server

## Summary
The server half of feature 10 (reference-aware rename) and of feature 15's
durability. A preview route lists what renaming a file or folder would change
(same-name siblings of the main document, the references in other files, the
settings that name it, what needs attention); an apply route makes the
confirmed part as one commit with `Aldine-Moves` / `Aldine-Meta` trailers, or
one undo image in a project that commits by hand. `/revert` and `/undo` read
those back and put names, text, the main document, the Zotero sync file,
review threads and the document state back. Renames (old and new routes) now
carry each file's Yjs state (highlights, agent marks) to the new path; a new
branch and a project copy start with the source's state. A title plan/apply
pair offers to change `\title{<old project name>}` when the project is renamed.
Nothing changes for a user until WP29's dialog calls the new routes, except:
highlights and agent marks now survive the plain rename, editors receive the
`moves` signal, and a rename that would give the main document a name the
compiler refuses is refused.

## Deviations
1. **Plan rows carry two extra fields.** `edits[].follows` is the `from` of the rename the edit depends on (a reference to `paper.bib` follows the `paper.bib` sibling's checkbox; WP29 needs it to make "references to a sibling follow that sibling's checkbox" work). `renames[].reason` explains `disabled: true` ("A file named … already exists"). Both are additions; the frozen fields are as specified.
2. **`edits[].before` / `after` are the whole source line** before and after the edit (only the path argument differs).
3. **Apply reply:** `{ok, newRoot?, commit?, undo?, renamed, edited, skipped, files, moves}` where `renamed`, `edited`, `skipped` are counts, `files` is the number of files whose text changed (for "updated 5 references in 3 files"), `moves` the `[from, to]` pairs made, and `undo` (manual commits only) the token for `POST …/undo`. Without commits there is no `commit`.
4. **Apply body:** `renames` may include the requested pair or not (it is always made); only siblings the plan offers, not disabled, are accepted, anything else is a 409. Edit ids not in the fresh plan are counted in `skipped`.
5. **Title routes:** `GET …/title-plan?branch&from=<old project name>&to=<new name>` (or POST with the same body) → `{offer, edits:[{id,file,line,kind:'code',before,after,checked}]}`; `POST …/title-apply {branch, from, to, edits?}` → `{ok, commit?, edited, undo?}`. The client renames the project itself (PATCH) and calls title-apply when the person says "Change title too". Matches are `\title{…}`/`\title[…]{…}` and hyperref's `pdftitle={…}` holding exactly `latexEscape(old name)`, outside comments, in the main document and the files it `\input`s/`\include`s.
6. **The `.gitignore` warning** of the report is not implemented (a sibling that is untracked and ignored is simply not committed; it still moves on disk).
7. **Per-branch root fallback** stays with WP30 (`compile.ts`), as the plan assigns it.

## Privacy notes
No new hosts, data or storage. The rename commit's trailers hold file paths only. Undo images (manual commits) also store the rename's moves and setting changes beside the file images in `META_DIR/undo`.

## For later packages
- **WP29 (rename-web):** call `GET /api/projects/:id/file/rename-plan?branch&from&to` (403 for viewers, 413 over the scan cap: offer "Rename only"); show no dialog when `renames.length === 1 && edits.length === 0 && unresolved.length === 0` and settings name only the main document or nothing (the plain rename does those itself). Apply with `POST …/file/rename-apply {branch, from, to, renames:[{from,to}…], edits:[id…]}`. Undo: `POST …/revert {branch, hashes:[<full or short commit>]}` (the reply's `newRoot` is the main document to show again), or `POST …/undo {branch, token}` with the apply's `undo` when there was no commit. Every apply, revert and undo sends the `moves` signal (`FilesMovedSignal`, folder pairs as plain paths), which WP06 turns into `filesMoved`.
- The plain `POST …/file/rename` also sends the `moves` signal now.
- Edit ids are stable for the same file, command, ordinal and old argument; a preview older than the text gives skipped edits, never wrong ones.
- Known limit (WP03's `moveDocState` rule, kept on purpose): renaming a file to a name that was deleted or renamed away less than 5 seconds earlier gives the moved file a fresh document state there (its highlights do not follow), because a client of the vacated name may still reconnect. Undo (revert or undo image) is exempt: it lifts the tombstone, since the state it returns is that name's own.
