# WP03 server-foundation

## Summary
The server half of the V2 foundations now exists: the feature host
(`registerFeatures`, called once from `app.ts` after `registerRoutes`), the
route kit features build their routes with, account preferences
(`/api/account/preferences`), project settings in `ProjectMeta.ext`
(`/api/projects/:id/settings`, filtered into every project reply), the
capabilities route (`/api/capabilities`), and the seven collab primitives in
`collab.ts`. Nothing changes for a user in wave 0: no shipped feature defines
a project setting or a route yet, the server probe registers only under
`ALDINE_TEST_HOOKS=1`, and the one tightening (`/api/references/search` needs
a sign-in when accounts are on) is the plan's.

## Deviations
Every signature in `srv/features/types.ts` and every collab primitive keeps
the frozen shape. Behaviour the contracts left open, or where the stub
comments said something slightly different:

1. **`flushBranchDocsHashed`** returns a hash for every loaded doc of a
   project file it flushed, whether or not the store rewrote the file (the
   stub said "every loaded doc it wrote"; an unchanged file is on disk as the
   hash says). Signal docs and tombstoned docs are left out. The map has no
   prototype (`Object.create(null)`). The hash normalises CR/CRLF to LF before
   hashing, so it equals the browser's hash of CodeMirror's text even for an
   un-migrated snapshot.
2. **`branchChangeEvents`**: paths are normalised (`path.posix.normalize`,
   the same key `fileVersion` uses); the event object and its `paths` are
   frozen; listeners run synchronously in the write (often under the repo
   lock), each in its own try/catch.
3. **`applySpansToDoc`** drops CRs from `after`, returns `[]` when the text is
   already `after` (the doc is still written), returns null for signal or
   non-project paths and for tombstoned docs, and marks the spans as Claude's
   when `origin === AGENT_ORIGIN` (as `applySuggestionToDoc` does).
4. **`moveDocState` writes no text.** The stub said "Flushes and evicts loaded
   docs first": it writes each loaded doc's latest *snapshot* (never its text,
   which would re-create the old file if the caller already renamed it), then
   evicts it exactly as `evictDoc` does (tombstone for 5 s, sockets closed).
   So it works before or after the disk rename; the caller flushes text first,
   as the rename route does today. When the target name has a loaded doc or a
   live tombstone, the source snapshot is deleted and the target keeps its
   identity (today's behaviour). A source with no snapshot also deletes any
   stale snapshot at the target. It bumps the files signal like
   `evictDoc`/`evictTree`. Trailing slashes on folder paths are ignored.
5. **`copyDocState`** prefers a loaded source doc's live state over its
   snapshot file, skips damaged snapshots, hidden/non-project paths, loaded
   *and tombstoned* targets (a just-deleted name's clients may reconnect),
   replaces any other snapshot at the target, and returns 0 for a copy onto
   itself.
6. **`signalBranch` throws** for the built-in keys `v a ts td c r` and for an
   empty key: a feature value there would make every editor refetch or
   typeset. Any JSON value is allowed; a repeated signal must carry a new value.
7. **Doc-load hooks** run only on the main load path (snapshot or seed), not on
   the multi-node path where the doc arrived from a peer node with its text
   (that node ran them). If any hook changed the doc, its snapshot is written
   at once.
8. **Side-map-only updates**: an update whose transaction did not touch the
   `content` Y.Text no longer calls `noteEdit` (keyed by the update bytes
   Hocuspocus hands to `onChange`). V1 clients write no side maps, so no V1
   behaviour changes.
9. **`registerFeatures`** registers the core routes first (`/api/capabilities`,
   `/api/account/preferences`, `/api/projects/:id/settings`), then each feature
   in manifest order; `feature.register` runs inside an encapsulated
   `app.register` plugin (hooks and decorators a feature adds stay on its own
   routes). A malformed feature (unknown or repeated id, a write allowance not
   matching `^(POST|PUT|PATCH|DELETE) /api/projects/:id(/…)*$`, a non-function
   hook) is skipped whole; a bad `projectSettings` entry is dropped alone; a
   throwing `register` is logged and keeps the routes it added. Registering a
   feature id again (a second app in one process) replaces its settings and
   doc-load hook.
10. **`ProjectSettingDef.id`** must be `<featureId>.<name>` (name
    `[A-Za-z0-9][A-Za-z0-9_.-]{0,80}`), enforced at registration; a
    definition without `validate` is dropped; a validator that throws counts
    as "invalid".
11. **`ext` bounds** (not in the plan): 64 keys per change, 16 KB per value
    (JSON), 128 KB for the whole `ext` (`EXT_LIMITS`). A change that changes
    nothing keeps the revision and sends no signal.
12. **`publicExt`** returns `undefined` (not `{}`) when no visible, valid key is
    set, so project replies stay byte-identical to V1; a stored value its
    definition now refuses is left out. `readExt` gives `undefined` for such a
    value and for `EXT_REV_KEY`.
13. **`RouteKit.limiter`** is an in-memory token bucket per node and caller
    (`clientKey`: the account, else the address), because the contract's
    signature is synchronous and the shared `RateLimiter` is async (Redis).
    Names are scoped per feature (`<featureId>:<name>`).
14. **`RouteKit.requireMember/requireOwner`** first run `requireAccess` (404 for
    a missing or trashed project, 401, 403, token scope), then refuse a
    showcase, then call routes.ts's own `requireMember`/`requireOwner` (same
    messages). A "Can view" collaborator is a member, as in V1; the global
    guard keeps them off writes not in `viewerWrites`.
15. **Account preferences** (plan §2.5 plus the analyst's value rules): a value
    is a boolean, a finite number, text up to 500 characters, or lists/objects
    of those nested at most 3 deep; `null` is refused (use `unset`). `PUT` is
    bounded by the stored maximum (300 keys, 32 KB), not by the 64-keys-per-request
    limit, so an import of more than 64 settings works. A PATCH or PUT that
    changes nothing keeps the revision. The rate limit is a dedicated
    `RateLimiter('preferences', 60, 2/s)` per account (not `visitLimiter`,
    which other routes share). Merges are serialised per account in-process
    (one app node, as `docs/SCALING.md` assumes for repositories).
16. **Project settings PATCH** also checks `canEdit` and refuses bearer tokens
    itself (the global guard already does both), and is rate limited
    (`RateLimiter('project-settings', 60, 1/s)`).
17. **Capabilities**: `rev` is the first 12 hex digits of the SHA-256 of the
    served `index.html` (it changes with every web build), `''` without a web
    build. `prefs` is true only for a signed-in, cookie (non-bearer) caller
    with accounts on. `oauthRegistration` = accounts on, `ALDINE_MCP=1` and
    `ALDINE_OAUTH_REGISTRATION` open. "Signed-out callers get a public subset":
    the base keys are public facts already exposed by `/api/auth/me` and the
    OAuth discovery documents, and each feature answers `kit.user(req) === null`
    with its public keys only (the contract has no per-key flag, so the host
    cannot filter). A feature that throws, answers a non-object or takes over
    2 s is left out of that reply. Features may replace base keys (WP45's
    webShell names `rev`). Bearer tokens get 403 from the global guard (the
    route is not in its "neutral" list).
18. **The server `_probe` feature** is active only under `ALDINE_TEST_HOOKS=1`
    (every Playwright config sets it; production must not). It defines
    `_probe.note` (visible, writable), `_probe.serverOnly` (server only) and
    `_probe.copied` (copyWithProject), the capability `probe`, `tokenWrites`
    and `viewerWrites` entries, a doc-load counter, and routes under
    `/api/projects/:id/_probe…` and `/api/_probe/limited`.

## Privacy notes
- **Account preferences** are stored in the datastore's `connections` table,
  row (user id, `laytekz-preferences`), as `{prefs, rev, updatedAt}`: at most
  300 keys and 32 KB per account. Written only by a signed-in browser session
  (never a bearer token), read only by the same account, deleted with the
  account (the existing `deleteUser` purge of `connections`). Nothing leaves
  the server. Request R1 adds them to the privacy page.
- **Project settings** live in `ProjectMeta.ext` with the project metadata.
  Keys marked `clientVisible` are sent to everyone who can open the project
  (members, viewers, link visitors, tokens with access), in
  `GET /api/projects/:id`, the project list and `/settings`; others never
  leave the server. Neither kind may ever hold a secret: a V1 server reading
  the same metadata would hand `ext` to clients unfiltered.
- **`/api/capabilities`** tells any caller whether accounts, MCP and OAuth
  client registration are on, and the web build's hash: facts the sign-in
  page and the OAuth discovery documents already expose.
- **Snapshot moves and copies** (`moveDocState`, `copyDocState`, wired by WP28
  in wave 3): a doc's side maps (agent marks, later highlights) follow a
  renamed file, a new branch and "Make a copy", so a copy's new owner gets
  the highlights and agent marks of the copied files. Files only under
  `META_DIR/yjs`, as today.
- No outbound hosts; no new cookies.

## For later packages
**Write a server feature** in `apps/server/src/features/<id>/server.ts`
(default export, `id` = your feature id; the manifest already imports it):

```ts
const feature: ServerFeature = {
  id: 'wordcount',
  projectSettings: [{ id: 'wordcount.rule', validate: isRule, clientWritable: true }],
  register(app, kit) {
    app.get('/api/projects/:id/wordcount/breakdown', async (req, reply) => {
      const meta = await kit.requireAccess(req, reply); if (!meta) return;
      return breakdown(meta.id, kit.readExt<Rule>(meta, 'wordcount.rule'));
    });
  },
};
export default feature;
```

- **Routes** go under `/api/projects/:id/...` (the kit's guards read
  `req.params.id`). Reads are open to everyone who can open the project,
  viewers and tokens included; writes are refused to bearer tokens and to
  "Can view" people unless listed in `tokenWrites` / `viewerWrites` as
  `'POST /api/projects/:id/references/insert'` (justify each in your notes).
  Showcases refuse every write. Use `kit.requireMember(req, reply, 'add
  references')` or `kit.requireOwner(...)` for writes; each replies itself and
  resolves null.
- **Project settings:** define each key (`<featureId>.<name>`) in
  `projectSettings`; the client's `SettingDef` of scope `project` uses the same
  id, and `useProjectSetting` reads/writes it through
  `GET/PATCH /api/projects/:id/settings` (WP02). Server code writes any
  defined key with `await kit.writeExt(projectId, { 'x.y': v }, ['x.z'])`
  (throws `ProjectSettingError` with `key`: answer 400). Never a secret, even
  with `clientVisible: false`. `copyWithProject: true` keys follow "Make a copy".
- **Capabilities:** `capabilities(req)` returns `{ myKey: … }` from memory;
  return only public keys when `kit.user(req)` is null. Clients read them with
  WP02's `useCapabilities()`.
- **Signals:** `kit.signal(projectId, branch | '*', 'myKey', value)` reaches
  the branch's open editors (`branchSignal.onSignal('myKey', fn)`, WP06); give
  each signal a new value. `settings` and `moves` already have meanings
  (D14); the built-in keys throw.
- **Doc loads:** `onDocLoad(doc, name)` tidies side maps in a transaction with
  a server origin, never the text.
- **Collab primitives** (import from `../../collab.js`):
  - WP21: `const sources = flushBranchDocsHashed(id, branch)` in place of the
    compile's `flushBranchDocs`; `sources[path]` equals the browser's
    `sha256(text).slice(0, 16)` (UTF-8, LF).
  - WP24/WP32: `branchChangeEvents.on('change', ({ projectId, branch, paths }) => cache.invalidate(...))`
    (`paths` null: everything); record and return, never do the work inside.
  - WP28: in the rename route, replace `evictDoc(id, b, from)` by
    `moveDocState(id, b, from, to)` and `evictTree(id, b, dir, files)` by
    `moveDocState(id, b, dir, newDir, { folder: true, files })` (after
    `flushBranchDocs`, before or after `fs.rename`); after
    `gitops.createBranch` call `copyDocState({ projectId: id, branch: from }, { projectId: id, branch: name }, paths)`,
    and in the copy route `copyDocState({ projectId: src, branch: 'main' }, { projectId: copy.id, branch: 'main' }, paths)`.
    Reference edits in open docs: `applySpansToDoc(id, b, file, newText, origin)`
    (null: no open doc, write the file). Send `signalBranch(id, b, FILES_MOVED_SIGNAL, { moves, by, at })`.
- **Tests:** server tests that need the probe set `ALDINE_TEST_HOOKS=1` before
  importing; `test/feature-host.test.mjs` shows the guard matrix.
