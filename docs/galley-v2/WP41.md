# WP41 desktop-settings-bib

## Summary
The desktop app has its own settings window (features 7 and 8 on the desktop). It holds the server address, "Open Laytekz when I log in", "When Laytekz opens" (the project list or the last project), page zoom (80–150%, kept across reloads and launches), spelling languages (Windows and Linux) and the list of linked local .bib files. It opens from Laytekz → Desktop App Settings…, Change Server… (at `#server`), the web app's Desktop button (`<base>/settings/desktop-app`), Settings… on a V1 server or offline, and File → Linked .bib files… (at `#bib`).

File → Link a local .bib… (with a project open) links a .bib file on this computer to the project. Behind it is a `desktop-file` library link (WP35's contract). The file is uploaded at once, then 1 s after each save while the app runs. Unlink, in the settings window, removes the link and stops the uploads. A link removed in the project's Libraries panel stops the watch at the next upload.

## Deviations
1. **Switching servers restarts the app** until R1 lands; see R1.
2. **Zoom, without `main.js`.** The WP09 notes suggested a request to apply the zoom on `did-finish-load` in `main.js`. Instead the feature hooks `app.on('web-contents-created')` and the window that already exists. It applies the stored factor on `did-finish-load` to every window of the server's session that shows the server. The View menu's zoom roles have no event, so a zoom changed there is kept at the next full navigation or reload (`did-start-navigation`), when the window closes, and when the settings window reads its state. A zoom outside 80–150% from the View menu is kept (allowed range 50–300%) and shown as an extra choice.
3. **Reopening the last project, without `main.js`.** The project list loads first, and on that first load of the run the feature loads `<base>/p/<id>[?branch=…]`. So for a moment the list shows before the project. It happens only when the first page of the run is the project list, never for `/settings` or a sign-in. The last project is recorded per server (at most 5 servers) from `did-navigate`/`did-navigate-in-page` on the server's windows. A `main.js` start-page hook would remove the flash; it is not requested, to keep `main.js` untouched.
4. **Unlinking lives in the settings window** (File → Linked .bib files… opens it at `#bib`), not in a menu entry per file. Feature menus are fixed when the host validates them, so a list of files cannot appear there. Each row has Upload now and Unlink. Rows for another server can only stop the local watch, and say so.
5. **Project file name.** The link asks for the local file's own name when it is a plain `.bib` name (`refs.bib`); otherwise the server picks one (`library.bib`). The server can answer `exists`. Then the app asks: Replace (`replace: true`), Use another name (the server's default) or Cancel. It answers `taken` or 400 for a refused name, and the app then falls back to the server's default.
6. **Spelling languages** show on Windows and Linux (both use Chromium's Hunspell dictionaries); macOS shows a note pointing to System Settings.
7. **Open at login** calls `app.setLoginItemSettings` only in a packaged build outside test mode. Elsewhere the choice is stored and the page says "Takes effect in the installed app." This keeps a source run or a test from registering Electron as a login item.
8. **Window background colour** (the automatic theme colour at launch, from the settings-theme report) is not built. It was not in WP41's list, and it needs `main.js`.
9. **Server switches and links.** Records belong to one server. After a switch (R1), the watch list follows within 3 s: the other server's watches stop and are kept, never pushed (so its 404 cannot drop them), and the new server's links are watched, with a catch-up upload.
10. **Cross-feature modules.** `desktopSettings/open.js` lets bibwatch's menu item open the settings page, and `bibwatch/api.js` hands the running watch list to the settings page. The host lets a feature open only its own pages.

## Privacy notes
- **settings.json (the app's profile folder)** gains:
  - `features.desktopSettings`: `openAtLogin`, `launch`, `zoomFactor`, `spellLanguages`, and `lastPaths` (`{<server base>: "/p/<id>[?branch=…]"}`, at most 5 servers). A value equal to its default is not written.
  - `features.bibwatch.links`: one record per linked file, `{server, projectId, branch, linkId, file, bibFile, hash, pushedAt}`. `file` is the absolute local path, so it can contain the computer's user name. `hash` is the SHA-256 of the last uploaded text.
- **What leaves the computer:** the text of a .bib file the person chose with File → Link a local .bib…. It goes only to the server it was linked on, only while the app runs, and through the window session (the person's own session cookie, no Origin header, `cache: no-store`). Requests: `POST /api/projects/:id/libraries` (`{provider: 'desktop-file', branch, bibFile?, replace?}`), `PUT …/libraries/:linkId/content` (`{content, branch}`) and `DELETE …/libraries/:linkId`. The server stores the text as the project's linked .bib (WP35) and records who linked it. The local path is never sent.
- **The server health check** (`GET <address>/api/health`, as Change Server… did) goes to an address the person types.
- **The OS login item list** gets Laytekz only when the person turns on "Open Laytekz when I log in" in the installed app.
- **No new hosts.** No secrets are stored. The remote page still has no preload; the settings page uses the shared `ui.cjs` bridge, served for that page alone.
