# WP09 desktop-shell

## Summary
The desktop app now has a shell feature host (`src/main/features/host.js`).
It validates and starts `SHELL_FEATURES` and gives each feature a `ShellCtx`:
menu items, its own local pages (CSP, preload, partition), strict IPC,
overlays, permission vetoes, a settings namespace, the server session and the
project a URL shows. The shell also:
- appends ` Laytekz-Desktop/<version>` to the remote session's user agent;
- has a Settings… item on Cmd/Ctrl+, that hands the page the cancelable
  `laytekz:open-settings` event;
- opens its own settings window for `<base>/settings/desktop-app`;
- loads feature-specific server mocks from `tests/mocks/*.mjs`.

For a user, two things change in the menu. Settings… (Cmd/Ctrl+,) is new, and
Change Server… lost that chord. On a V1 server, Settings… opens Change Server,
which is what Cmd/Ctrl+, did in desktop 1.0. The three shipped shell features
are still stubs and add nothing.

## Deviations
The contract is `desktop-v2/src/main/features/index.js` (frozen, unchanged).
These points fill in shapes it leaves open, or depart from plan §2.8:

1. **`ShellCtx.server()`** returns `server.base`: the origin plus any base path, with no trailing slash.
2. **`ShellCtx.settings`** stores values nested, as `settings.json` → `features: { <id>: { <key>: value } }`.
   - Keys must match `/^[A-Za-z][A-Za-z0-9_.-]{0,63}$/`.
   - Values are JSON. `set(key, undefined)` deletes the key, and `get` returns a copy. Invalid input throws a `TypeError`.
3. **`ShellCtx.sessionFetch(path, init)`** takes a path starting with a single `/`; anything else, or no server, rejects.
   - Defaults are `credentials: 'include'` and `cache: 'no-store'`, and the caller's `init` overrides them.
   - Nothing adds an `Origin` header. The test shows the mock receiving `origin: null` and the session cookie.
4. **`ShellCtx.ipc.handle(channel, fn, {pages})`**:
   - Channels look like `<prefix>:<name>`. The pages must be ones the feature declared in `pages`, or its `settingsPage`.
   - A refused call resolves `null`; an invalid registration throws. Registering the same channel twice for the same page throws.
   - Two features may share a channel name for different pages.
   - **`ui:get-state` and `ui:action` may be served** for the feature's own pages. This is how a page on the shared `ui.cjs` preload talks to its feature, because WP41 owns no preload. `ui-bridge.js` asks the host only when no built-in `bindUi` handler serves the sender. Every other `ui:*` channel is refused.
   - The sender check requires all of these: the sender is a webContents the host created for that feature and page; the frame is the top frame; and the frame URL, without its `#fragment`, is exactly `laytekz-ui://app/<page>`.
5. **`ShellCtx.openLocalWindow(page, opts)`**:
   - `opts` takes `{title, width, height, minWidth, minHeight, resizable, minimizable, maximizable, modal, parent, background, hash}`. Every other key is ignored, `webPreferences` included.
   - There is one window per feature and page. A second call focuses the open window and returns it, and with `hash` it sets `location.hash`.
   - `parent: true` makes the main window the parent. `modal` applies only with a parent and never in test mode.
6. **`ShellCtx.overlay(page, opts)`**:
   - `opts` takes `{bounds(width, height) → {x, y, width, height}, background}`.
   - It returns `{show(), hide(), raise(), layout(), destroy(), visible, contents, view, window}`. The view is created on the first `show()`, and the toast is raised above it after each show.
   - It throws when there is no main window. An overlay belongs to the main window that existed when it was made, so make a new one after the window is re-created.
7. **Settings… fallback.** The plan says "falls back to loading /settings". Here:
   - The event goes to the front window if it shows the server, otherwise to the main window. It is dispatched from an isolated world with `detail: null` and `cancelable: true`.
   - If it is not cancelled, the shell loads `/settings` only when the server answers `/api/capabilities` (V2). On a V1 server, which has no settings page, it opens the desktop settings page instead, which is what desktop 1.0 did on that chord. This follows plan §4.4: "desktop 2.0 feature-detects through `/api/capabilities` and degrades gracefully".
   - When the offline screen is up, it opens the desktop settings page.
   - When the page does not answer within 3 s, it does nothing.
8. **Change Server…** (the menu item and the offline screen's button) now opens the settings page at `#server`. While `desktopSettings.settingsPage` is `change-server.html`, that is today's dialog. Once WP41 names its own page, Change Server… opens that page at `#server`, with no change to `menu.js`, which freezes after wave 0.
9. **The intercept** covers `window.open`, `will-navigate`, `will-redirect` and `loadInWindow` for exactly `<base>/settings/desktop-app` (optionally with a trailing `/`), with any query or fragment.
   - It does not cover in-page `history.pushState`. The web app's button must use `window.open(withBase('/settings/desktop-app'))` or a full navigation.
   - Repeats from a page within 1 s are ignored, so a page cannot keep stealing focus.
10. **Validation.**
    - Invalid parts of a feature are dropped and reported in `host.problems`, which are logged as `Laytekz: …` warnings and never thrown. This mirrors the web registry (D6).
    - Every menu item needs an `id`, unique across features and the core ids.
    - A feature item's accelerator is removed when a web chord (`rules.js WEB_CHORDS`: V1's chords plus plan §2.3's) or the app menu already holds it; the item itself stays.
    - A `start()` that throws or rejects stops the feature. Its menu items, vetoes, IPC handlers and settings page are withdrawn, and the menu is rebuilt. `start()` may also return a Promise of its stop function.
    - Feature menu clicks that throw are logged, never raised.
11. **`vetoPermissions`** apply from the host's creation, which is before the first page load, until quit, for every listed feature that has not failed.
12. **Feature ids.** The host accepts any `/^[A-Za-z][A-Za-z0-9_-]{0,31}$/` id, not only the typedef's three, so the test probe can run. The shipped list is unchanged.
13. **Menu placement**, which the plan leaves open:
    - `app`: on macOS, the app menu after Change Server…; on Windows, the File menu after Change Server….
    - `file`: on macOS, a File menu created when non-empty; on Windows, the File menu after a separator.
    - `view`: after Toggle Developer Tools.
    - `help`: after Privacy.
14. **`protocol.js`** also serves `.png` and `.woff2`. The flat-name rule is unchanged.
15. **No code change for the context menu.** The plan asks WP09 to prove that cancelling the DOM `contextmenu` event suppresses Electron's `'context-menu'`. It does, with real macOS spelling suggestions in the hidden test window.

## Privacy notes
- **User agent.** ` Laytekz-Desktop/<version>` goes on every request the remote session makes.
  - That covers the configured server, its health and sign-in requests, and any third-party page shown in the in-app integration auth window, since it shares the session.
  - It tells them the desktop app is in use and which version. Electron's default user agent already carries the app name and version and the Electron version.
- **`GET <server>/api/capabilities`**, without cookies, when Settings… finds the event unhandled. Only the answer from a V2 server is kept, in memory.
- **`settings.json`** (the profile folder) gains `features.<id>.*`, written only by shell features. The wave-0 stubs write nothing; the test probe writes `startedWith` and `stopped`.
- No new hosts, no new stored secrets, and no new IPC reachable from the remote page, which still has no preload.

## For later packages
- **Writing a shell feature** (WP17, WP25, WP41): fill `src/main/features/<id>/index.js`. Never import `electron` at the top level; use `const { app } = await import('electron')` inside `start` if you must. Example:
  ```js
  const feature = { id: 'console', pages: { 'console.html': { partition: 'laytekz-console', preload: 'console.cjs', csp: CSP } },
    menu: [{ where: 'view', item: { id: 'console-toggle', label: 'Console', accelerator: 'Control+`', click: () => panel?.toggle() } }],
    vetoPermissions: ['clipboard-read'], start(ctx) { ctx.ipc.handle('console:open', (e, opts) => open(e.sender, opts), { pages: ['console.html'] }); return () => killAll(); } };
  ```
- **Local pages:**
  - Pages live under `src/ui` and need flat names.
  - A page without `preload` gets none. To use the shared bridge (`window.laytekz.state/action/onState`), declare `preload: 'ui.cjs'` and serve `ui:get-state` and `ui:action` with `ctx.ipc.handle(…, {pages: [page]})`.
  - To push state, call `webContents.send('ui:state', state)` on the window `openLocalWindow` returned, or on the `event.sender` a call came from.
  - A partition of your own (`laytekz-<name>` or `persist:laytekz-<name>`) gets the `laytekz-ui://` scheme and the UI session's hardening: no network, no permissions, no downloads.
  - Your `csp` replaces `UI_CSP` for that page only.
- **WP41:**
  - Set `settingsPage: 'desktop-settings.html'` in `desktopSettings`, and declare it in `pages` with `preload: 'ui.cjs'`.
  - The intercept, Settings… on a V1 server or offline, Change Server… (`#server`) and the offline screen's button then all open it. Read `location.hash` and listen for `hashchange`.
  - Add a "Desktop App Settings…" item through `menu` that calls `ctx.openLocalWindow('desktop-settings.html')`; it reuses the same window.
  - `main.js` is integrator-only from wave 1. These need requests: applying a zoom factor on `did-finish-load`, the start-up page ("reopen the last project"), and the window background colour.
- **WP17:** `ctx.overlay(page, {bounds})` returns a handle; re-run `bounds` with `layout()`. Make a new overlay after the main window is re-created (macOS reopen); `ctx.mainWindow()` tells you which window is current.
- **Mocks:** a feature's server routes go in `tests/mocks/<id>.mjs`, exporting `handle(req, res, ctx)` (see the header of `tests/mock-server.mjs`). `tests/mocks/libraries.mjs` is WP41's.
- **Web side (WP04, WP06, WP07, WP23):**
  - Mod+, must be a `desktop: 'native-menu'` binding so the web skips it in the desktop app. If the page took it, the menu item would never fire.
  - Handle `laytekz:open-settings` and call `preventDefault()`.
  - The Desktop button must use `window.open`.
