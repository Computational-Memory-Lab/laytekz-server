# WP29 rename-web

## Summary
The web half of feature 10. Renaming or moving a file (tree menu, F2, drag,
palette) first asks the server what else would change (WP28's plan). When
nothing else refers to the file, the page renames it exactly as before. When
other files refer to it, or files beside the main document share its name,
a preview dialog lists the files, the references (a one-line diff each), the
settings that follow, and what needs attention; the confirmed part is applied
as one commit, and the notification's Undo puts names, text and the main
document back. Renaming the project offers to change a `\title` that still
holds the old name. A collaborator with the renamed file open follows it to
the new path (WP06) and is told who renamed it.

## Requests

### R1: a rename the person cancelled, and a drag the feature already reported (contract + Editor.tsx + FileTree.tsx)
- **Contract** (`apps/web/src/features/types.ts`, `Interceptors.fileRename`): the result may also be `'cancelled'`:
  `fileRename(r, p): Promise<'handled' | 'default' | 'cancelled'>`; `intercept()` in `features/pageCtx.ts` stops on it as on `'handled'` and returns it.
- **Anchor** (Editor.tsx): `if ((await interceptFileRename(modules, { from, to, via }, page)) === 'handled') return true;`
- **Hunk:**
  ```diff
  -                  if ((await interceptFileRename(modules, { from, to, via }, page)) === 'handled') return true;
  +                  // Galley: V2 interceptors: 'cancelled' leaves the tree as it was; 'handled' was reported by the feature
  +                  const by = await interceptFileRename(modules, { from, to, via }, page);
  +                  if (by === 'cancelled') return false;
  +                  if (by === 'handled') return 'reported';
  ```
  and in `FileTree.tsx`: `onRename(...): Promise<boolean | 'reported'>`; the drop handler shows its "Moved … to …" toast only when the result is `true` (`'reported'` still counts as renamed for `rename()`).
- **Why:** the interceptor can only answer `'handled'` or `'default'`. A cancelled preview has to answer `'handled'` (`'default'` would rename), so the tree treats it as done.
- **Without it:** cancelling the preview leaves the files as they were, but for a drag the tree still shows "Moved x to folder/" and its Undo then fails with "No file named …". A confirmed drag shows the tree's toast as well as the rename's (the rename's Undo is the one that puts references back). For F2 or the menu, focus moves to a row that does not exist (harmless). `flow.ts` returns `'handled'` on cancel; switch it to `'cancelled'` when R1 lands.

### R2: Home's project rename names the project (contract)
- **Contract:** `Interceptors.projectRename(r: { from: string; to: string; projectId?: string }, p: EditorPageCtx | null)`, with Home passing `projectId: p.id` (anchor in Home.tsx: `if ((await interceptProjectRename(modules, { from: p.name, to: name.trim() }, null)) === 'handled') { load(); return; }` → `{ from: p.name, to: name.trim(), projectId: p.id }`).
- **Why:** with `page: null` the interceptor knows neither the project nor the branch, so it cannot ask the server whether `\title` still holds the old name.
- **Without it:** the title question is asked when the project is renamed in the editor (toolbar name, or the name in the settings page over the editor), not on Home.

## Deviations
1. **A rename that touches nothing else is the page's own** (`'default'`), not an apply: the server's plain `/file/rename` already moves the main document, the Zotero sync file, review threads and (WP28) the document state, and sends the moves signal. It goes into the autosave commit as in V1, and a drag keeps the tree's own Undo. This keeps the V1 tree specs (58, 59, 65, 72, 08) unchanged. The report's "now as its own commit" is not done for that case.
2. **"Rename only paper.tex" and "Never" mode use `rename-apply` with no siblings and no edits**, so they are one commit with an Undo (Never: an Update that reverts that commit and opens the preview for the same rename).
3. **"Never" mode renames plainly when nothing outside comments would be left on the old name**, so the Update toast appears only when it matters.
4. **`rename.title` is `automatic: true`**: it interrupts a rename with a question, so it sits with the automatic behaviours, and the legacy specs' `automatic-off` test default keeps it out of specs that rename projects (27, 50, 54, 06). `rename.references` (Ask / Always / Never, default Ask) and `rename.siblings` (on) are plain settings in Files and outputs.
5. **The title question is the app's own confirm dialog** (`page.confirm`: "Also change the document title?", the one-line diff, **Change title too** / **Only rename the project**). Dismissing it means "Only rename the project". When the question was asked, the feature renames the project itself (PATCH), then applies the title as one commit; a refused PATCH returns `'default'` so the page tries again and shows its own error.
6. **Over the scan cap (413)** the page renames plainly and a notification says the references were not checked (no dialog with "Rename only").
7. **Not built:** ⌘Z in the renamed file straight after the rename (the report's step 4). The notification's Undo and History do it.
8. **Peers:** WP06 already moves a collaborator's open file on the moves signal; this package adds the "Ada renamed intro.tex to introduction.tex" notice (not for this tab's own renames or undos) and moves file spots, folders included, with `fileSpots.rename`.
9. **When the moves signal does not arrive within 2.5 s** (a dropped connection), the tab follows by itself: it opens the open file's new path and reloads the tree. It never reloads the tree before the signal, because a reload that misses the open file would trigger the "removed by someone else" toast.
