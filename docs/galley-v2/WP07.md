# WP07 settings-shell

## Summary
The registry-driven settings page now exists (`pages/Settings.tsx`): every
section of the registry in one scrolling column beside a section nav, each
setting drawn by a generic control with a scope badge ("This browser", "Your
account", "This project"), and the rows that already worked in V1's two
dialogs embedded unchanged (the project's rows, the account's identity,
connections and password, the shortcut recorders, this browser's name
without accounts). The V1 test ids stay on the same controls. The e2e
fixture sets `aldine.settings.testDefaults=automatic-off` in every browser
context unless a spec opts out. Nothing changes for a user until the page
host (WP06) routes to the page; V1's Project settings and Account settings
dialogs render exactly the DOM they rendered before, now built from the
same exported parts.

## Deviations
None from the frozen contracts: `pages/Settings.tsx` keeps `export default function Settings(props: SettingsPageProps)`, and `ProjectSettings`'s props (which `SettingsPageProps.project` is typed from) are unchanged. Decisions where the plan left room:
- The page is built on `components/Modal` (`role="dialog"`, `aria-modal`): the editor's own keys already stand down for an open dialog (Editor.tsx `dialogOpen()`, the palette), Escape and Close call `onClose`, a confirmation opened from inside stacks above it, focus returns to the opener. Its backdrop sits at `var(--z-settings, 150)`, under `--z-modal` dialogs.
- Close is in a footer action row (`.modal__row`, as V1's dialogs have it), not in a header: the V1 specs that measure the dialog's action row (30, 64) hold on the page too. The header holds the title only; WP23 adds search and the sync status there.
- A setting with a V1 test id whose control is `segmented` (only `appearance.theme`, which WP02 made segmented) is drawn as a native `<select>`, because spec 27 and 54 drive it with `selectOption`. All other segmented controls are radio groups.
- "Listed under Automatic changes" is read as: inside each section, `automatic` rows come after the others under a sub-heading "Automatic changes".
- `scopeName`: an account setting is badged "Your account" only while accounts are on and someone is signed in; otherwise "This browser" (it lives there). WP23 may refine it with the sync switch and status.
- Project-scope settings are shown only over a project (`/p/<id>/settings/*`); their rows are disabled unless `useProjectSetting` says `canEdit` and the page's project allows edits (not a viewer, not a showcase).
- Nav clicks scroll the column and replace the address with `/settings/<section>` or `/p/<id>/settings/<section>` (search kept, so `?branch=` survives), so history does not grow.
- Without accounts, the Account section shows "Your name" (this browser), using the editor's `onSetYourName` over a project (presence follows) and `api.setLocalName` on `/settings`.
- A section draws its embedded rows first, then its generic rows, then the automatic ones; the Account section splits its embedded rows so its settings (WP02's "Keep my settings in my account") sit between who you are and the commit email, sign-in methods and password.
- After a password change the page closes, as V1's Account settings dialog did (auth spec "change password" expects it).

## For later packages
- **Using the page** (WP06 renders it): `const Settings = lazy(() => import('./pages/Settings'))`, then `<Settings section={sectionFromPath} setting={decodedHash} project={projectSettingsPropsOrNull} onClose={back} />`. `project` is exactly the props Editor.tsx gives `ProjectSettings` today, less `onClose` and `focus`. The page needs a Router (it uses `Link` and `useLocation`), the Toast, Dialog and Auth providers. The `/settings/desktop-app` path must arrive as `section="desktop"`.
- **Test ids:** root `settings-page` (the dialog), `settings-nav`, `settings-nav-<section>` (with `aria-current="true"` on the section in view), `settings-content`, `settings-section-<section>`, `settings-section-<section>-automatic`, `setting-<id>` (the row; `data-target="true"` when a `#<id>` link named it), `setting-<id>-control` (the control; the V1 ids for theme, auto-typeset, vim, spellcheck, spellcheck language), `setting-<id>-scope`, `setting-<id>-hint`, `settings-close`. V1 ids kept: `project-settings` (around the whole column over a project), `settings-this-project` and every project row id, `settings-shortcuts` and `shortcut-*`, `settings-your-name`, `account-settings` (around the Account and Connections sections while signed in) and every account, token, git-host, template, Zotero, sign-in-method and password id.
- **A feature's settings appear by themselves**: a definition in `features/<id>/settings.ts` lands in its `section`, ordered by `order`, drawn by its `control`. `visible(env)` hides it (a throw hides it too); `dependsOn` disables it with "Turn on “<label>” first"; `applies: 'reopen'` adds "Applies when you reopen the file"; `automatic: true` lists it under "Automatic changes"; scope `project` shows it only over a project. A `custom` control is loaded lazily with `CustomControlProps` (`def`, `value`, `onChange`, `disabled`); one that throws shows "This setting could not be shown" in its own row only.
- **Deep links:** `openSettings({ section: 'typing', setting: 'escape.on' })` (WP02) leads to `/p/<id>/settings/typing#escape.on`; the page scrolls that row to the middle of the column, highlights it and focuses its control. Embedded anchors: `#sign-in` (sign-in methods), `#keys.shortcuts` (the shortcut rows), `#your-name`.
- **e2e:** every spec gets `aldine.settings.testDefaults=automatic-off` in all its browser contexts; a spec of an automatic feature writes `test.use({ settingsTestDefaults: null })` at file or describe level. `TEST_DEFAULTS_KEY` is exported from `e2e/fixtures.ts`. Helpers: `openProjectSettings(page)` and `closeSettings(page)` work for the V1 dialog and the page alike; `openSettingsPage(page, { section, setting })` opens the page through `laytekz:open-settings`.
- **WP23** extends this page: the header (search through `paletteRank`, sync status), row reset (each row has room in `.settings-row__head`), section and global reset, import/export, `TypographyPreview`, chips on phones (the phone nav is already one scrolling row), the Shortcuts section (the embedded `ShortcutRow`s use `util/shortcuts`, which WP04 keeps; WP02's `keys.shortcuts` is `visible: never` and also listed in `EMBEDDED_SETTING_IDS`), Desktop and Labs sections, and retiring the dialogs: `ProjectRows`, `AccountIdentity`, `PasswordForm`/`usePasswordChange` and the exported connection blocks are what the page already uses, so deleting the dialogs' default exports leaves the page intact.
- **V1 dialog layout assertions that do not carry over** once an entry point opens the page instead of a dialog: `auth-tests/tokens.spec.ts` `clearOfFooter` reads `account-settings > div > .modal__row` and expects the Create token button in view without scrolling (on the page Account comes before Connections, and the footer is outside the column); spec 30 `clippedByModal` and spec 64's `.modal .modal__row` still hold on the page.
