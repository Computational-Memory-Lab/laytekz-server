# WP04 input-core

## Summary
The input plumbing V2 features plug into now exists: one keybinding registry
(core and feature bindings, user overrides, the reserved-chord list, live
labels, dispatch through `bindingFor`) with a collision test that enforces the
plan's keyboard table; the command adapter (palette rows with roles, `when`
and chord hints; "Turn X on/off" for `palette: true` switches); the editor's
context-menu host and its policy; key chains (today's Tab and Escape moved in
unchanged); and the mod-click arbiter with its hint and Alt+Enter follow.
`util/shortcuts.ts` keeps every V1 export and delegates to the registry. For a
user nothing changes in wave 0 except what the shortcut recorder accepts (see
Deviations 4): the editor installs key chains, mod-click and the menu only
through WP05's host, and the menu never opens without a feature's items.

## Deviations
Contract signatures are unchanged; these are additions and decisions.

1. **Registry additions** (`keys/registry.ts`): `SHORTCUTS_KEY = 'aldine.shortcuts'`; `CORE_KEYBINDINGS: readonly KeybindingDef[]`; `keybinding(id): KeybindingDef | null`; `isOverridden(id): boolean` (a chord or a clear is stored); `chordConflict(id): string | null` (label of another binding on the same keys now); `subscribeKeybindings(fn): () => void` (override or registration changes). `RESERVED` is built from `keys/reserved.ts` (`RESERVATIONS`, `reservationFor(c, mac)`; editor-owned entries read "Bold in the editor").
2. **Two core bindings beyond V1's five:** `settings` (`mod+,`, scope `page`, `desktop: 'native-menu'`, command `settings`, group General) and `follow` (`alt+Enter`, scope `editor`, command `follow`, group Editor). The plan's table has both rows but no owner; a feature cannot own them. V1's five keep ids, labels and defaults (`comment` on ⇧⌘C, README D7). `registerKeybindings` skips (with a warning, never a throw) a duplicate id, a malformed default, an unknown scope or a missing command.
3. **Overrides go through the settings store** when it answers: `getSetting/setSetting/subscribeSetting(CORE_SETTING_IDS.shortcuts)`, and `resetSetting` when the last override goes. When the store throws (WP01's stub, an isolated build) the registry uses V1's own storage and `storage` listener, so shortcuts work either way. Stored shape: `{ [binding id]: Chord | null }`, `null` = cleared (unbound). Entries for ids this page has not registered are kept on every write (V1 dropped unknown ids). `changeable: false` bindings ignore overrides and refuse `setChord`. `chordFor(id)` returns a stored chord even for an id not registered on this page. This relies on WP02's `keys.shortcuts` accepting `Record<string, Chord | null>` (its working copy's `isShortcutOverrides` and `shortcutsCodec` do; the codec drops malformed entries, which V1 also never wrote back).
4. **`util/shortcuts.ts` semantics** (every V1 export kept): `chordFor(ShortcutId)` still returns a `Chord` (a cleared binding reports its default there; `matchesShortcut` and `useShortcutLabel` see the clear: no match, `''`). `setChord(id, null)` still means "reset" (it sets the default, which removes the override); the registry's own `setChord(id, null)` means "clear", as the contract says. `chordProblem` and `chordConflict` now look at every binding and at `RESERVED`, so **the V1 shortcut recorder refuses more chords**: ⇧⌘I/J and ⇧⌘C (except for comment: its own default), ⇧⌘A/B/D/O/P, ⇧⌘[ and ⇧⌘], ⇧⌘L, ⌘0/=/−, ⌘M, ⌘H, ⌘`, ⇧⌥F (Format document), Shift+F10, ⇧⌘Y on a Mac, every ⌘⌥/Ctrl+Alt chord (AltGr), ⌘, ("already Open settings") and ⌥↩ ("already Follow …"); and it now **accepts** Alt+Enter, Shift+Alt+Enter, ⇧⌥A and ⌥\ without ⌘ (plan §2.3). A binding may always take its own default back. Chords already stored keep working.
5. **Chord helpers** (`keys/chords.ts`, re-exported under the V1 names): `matchesChord` compares `key` case-insensitively, so a default on a named key (`alt+Enter`) needs no `code` (such a chord never matched before; nothing V1 stored had one). The identity `sameChord` uses lower case for F-keys and the physical key for punctuation codes (Option+\ types « on a Mac, Shift+/ types ?), so ⇧⌘/ recorded as `?` now equals `mod+shift+/`. Also exported: `chord('mod+shift+e', code?)`, `codeForKey`, `normalKey`, `chordId`, `isChord`, `keyFromCode`, `modHeld`, `MODIFIER_KEYS`.
6. **Key chains:** besides Tab completion 100 / indent 0 and Escape completion 100, `keyChainsExtension()` has **Shift-Tab → `indentLess` at 0** (the shift half of today's `indentWithTab`). Core entry ids: `core.acceptCompletion`, `core.indent`, `core.outdent`, `core.closeCompletion`. The keymap is one `Prec.highest` binding per chain key; a key whose chain declines falls through to the rest of the editor's keymaps, and an entry that throws is skipped with a warning. Also exported: `CHAIN_KEYS`, `CORE_CHAIN`, `chainFor(state, key)`, `runChain(view, key)`.
7. **Mod-click:** the modifier for clicks is ⌘ without Ctrl on a Mac (Ctrl-click is a right-click there) and Ctrl elsewhere (not the Windows key, unlike keyboard chords), never with Alt. The keyboard follow is the `follow` binding (`matchesShortcut(e, 'follow')`, Alt+Enter by default), not a hard-coded Alt+Enter, so it can be rebound. A target with `error` is underlined in the error style and its hint shown; it is never run. Drag threshold 5 px; the hint (`data-testid="modclick-hint"`, title plus "⌘-click to follow" or the error) comes 300 ms after the underline (`.cm-modclick-target`, `--error`); both go with the next edit or caret move. Also exported: `FOLLOW_BINDING`, `MOD_CLICK_DRAG_PX`, `HINT_DELAY_MS`, `PickedTarget`, `modClickHandlers(state)`, `pickTarget`, `modClickTargetAt(view, pos)`, `modClickHeld(e, mac?)`, `isModClick(e, mac?)`, `withinDrag`, `followAtCaret(view, e?)`.
8. **Context menu:** the policy is `contextmenu/policy.ts` (`menuPolicy`, `collectMenu`, `finishMenu`, `GROUP_ORDER`, re-exported from `contextmenu/index.ts`). It **never opens unless some entry returns items** (the plan's "opens inside a selection" would otherwise replace the native menu, spelling suggestions included, with a bare Cut/Copy/Paste). `MenuTarget.hadSelection` is true only when the menu opened inside a selection that existed before the press (keyboard: a selection exists), so a claimed link outside the selection does not hand a highlighter the old selection; `MenuTarget.selection` is that recorded selection, which is put back if the browser moved it. A Mac's Control-click inside the selection is kept from CodeMirror (which would collapse the selection on mouseup, unlike a native text field) while the menu setting is on; elsewhere CodeMirror handles it as before. `ctx` is `contextAt(state, pos)`, null while WP08's stub throws. The menu ends with Cut, Copy (`execCommand`) and Paste (`clipboard.readText` plus a synthetic paste event; on refusal the toast "The browser blocked pasting from this menu. Press ⌘V."), test ids `editor-menu-cut|copy|paste`, Cut/Copy disabled without a selection, Cut/Paste disabled when read-only; a mouse-opened menu adds the hint row "Shift+right-click for the standard menu" (`editor-menu-native-hint`). Shift+F10 and the Menu key open it at the caret; a `contextmenu` event without a fresh right-button press is left alone. The menu's test id is `editor-context-menu`, its label "Editor".
9. **`openMenu(o: OpenMenuOptions): { close(): void }`** (Menu.tsx): `OpenMenuOptions` is `MenuProps` without `onClose`, plus an optional `onClose(reason)`; one React root per open menu, unmounted after it closes. WP05's PDF menu may use it too.
10. **Commands:** `paletteCommands` drops a row with `when` when there is no page (Home); a row with `keybinding` takes the binding's live label as its hint, and none when the binding is cleared (a static `hint` is used only without `keybinding`); rows carry only the `Command` fields. `settingToggleCommands` skips project-scope settings, switches whose `dependsOn` is off, settings it cannot read, and the six with hand-written toggles (`EXISTING_TOGGLE_COMMANDS`: `editor.vim`→`vim`, `editor.spellcheck`→`spell`, `typesetting.auto`→`auto`, `typesetting.draft`→`draft-typeset`, `editor.changeMarks`→`change-marks`, `labs.agentPresence`→`experimental-agent`). Group `SETTINGS_GROUP = 'Settings'`; the title lower-cases the label's first letter unless the first word is an acronym or a proper noun ("Turn line numbers off", "Turn PDF dark mode on", "Turn Vim-style search on") and reads the value when called.

## Privacy notes
- Keyboard shortcut overrides stay in localStorage `aldine.shortcuts` as in V1; through WP02's store they are also account scope (`keys.shortcuts`), so a signed-in person's chosen chords are stored with their account's preferences on the server. WP02 defines that scope.
- The context menu's Paste reads the clipboard only when the person chooses Paste (`navigator.clipboard.readText`; the browser may ask first). Cut and Copy write it only on their click.
- WP04 contacts no host. What a mod-click opens is decided by the feature's handler (WP20 opens links).

## For later packages
- **A feature's keys and commands** (`features/<id>/index.ts`): declare the binding and a command with the same id; WP06 registers the binding and dispatches it, and the palette shows its chord.
  ```ts
  keybindings: [{ id: 'citations.insert', label: 'Insert citation', group: 'Citations', default: chord('mod+shift+e'), changeable: true, scope: 'page', command: 'citations.insert' }],
  commands: (page) => [{ id: 'citations.insert', group: 'Insert', title: 'Insert citation…', keybinding: 'citations.insert', refusedFor: ['viewer', 'showcase'], run: () => openPicker(page) }],
  ```
  (`chord` from `keys/chords`.) Use `scope: 'editor'` for keys that only make sense in the editor (WP05 dispatches them), `'page-capture'` for keys CodeMirror would otherwise take (like comment), `matchCode: true` for Option chords (⇧⌥A, ⌥\), `desktop: 'native-menu'` when the desktop menu owns the chord. The collision test (`keys/__tests__/collisions.test.ts`) fails if a default collides, is reserved, types a character, or takes a planned chord that belongs to another feature (its `PLANNED` table is the plan's §2.3 rows with their owners). Labels outside React: `chordLabel(id)`; in React: `useChordLabel(id)`.
- **Key chains:** `editor: { keyChains: [{ key: 'Tab', priority: KEY_CHAIN_PRIORITY.Tab.mathTabOut, id: 'automath.tabOut', run: tabOut }] }`; return false to pass the key on. Completion (100) and indent (0) are already in the Tab chain, completion (100) in Escape.
- **Mod-click:** `editor: { modClick: [{ id: 'links.url', priority: 50, target: (view, pos) => urlAt(view.state, pos) /* {from, to, title, error?} */, run: (view, t, e) => openExternal(t) }] }`. `run` gets a MouseEvent (on click, popup-safe) or the KeyboardEvent of the `follow` binding. A palette "Open the link at the cursor" command calls `followAtCaret(page.view()!)`.
- **Context menu:** `contextMenu: [{ id: 'highlighter.apply', group: 'annotate', order: 10, items: (t) => t.hadSelection ? [{ id: 'hl', label: 'Highlight yellow', onSelect: () => paint(t.view) }] : null }]`; add `claims: (t) => !!urlAt(t.view.state, t.pos)` for targets that open the menu without a selection. Never add Cut/Copy/Paste yourself.
- **Palette toggles:** mark a switch `palette: true`; WP06 rebuilds the rows when settings change (`settingToggleCommands` reads values when called).
- **Desktop (WP09):** `desk/tests/shell.spec.mjs` mirrors `CORE_KEYBINDINGS` and the `PLANNED` table; ⌘, is the Settings binding, `desktop: 'native-menu'`.
- **Menus from non-React code:** `openMenu({ items, anchor: { type: 'point', x, y }, label, testId, returnFocus })` returns `{ close }`.
